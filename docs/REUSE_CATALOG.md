# Готовые инструменты и код: что переиспользовать в YAN Agent Lab

Проверено по репозиториям и README: **2026-10-11**.

Этот документ сохраняет ранее обсуждённые проекты и конкретные места применения.
Запись в каталоге означает «учесть при выборе решения», а не «уже интегрировано».
Решение пользователя — использовать готовые инструменты, когда они закрывают задачу,
и не терять их из рассмотрения между чатами. Наша база уже является форком mcbuild.

## Решение перед написанием новой подсистемы

1. Проверить существующие модули нашей базы и этот каталог.
2. Выбрать способ: использовать имеющееся → подключить инструмент/API → адаптировать
   подходящий модуль → написать недостающую часть.
3. В PR или документе решения кратко записать рассмотренный проект, конкретный модуль,
   способ применения и причину выбора/откладывания. Не требовать отдельного исследования
   для каждой мелкой правки.
4. Отложенный инструмент остаётся в каталоге с причиной и условием возвращения.
   Отсутствие интеграции сейчас не является отказом от инструмента навсегда.
5. При переносе кода фиксировать upstream commit и сохранять notices. Метаданные лицензии
   ниже — ориентир для выбора; проверять LICENSE конкретных переносимых файлов.

### Minecraft Agentic Builder — конкретные кандидаты

- [`src/ops.js`](https://github.com/NoblerWorks-HQ/minecraft-agentic/blob/master/src/ops.js):
  выразить сооружение операциями вроде walls/floor/window, а не перечислением блоков.
  Сначала сопоставить с нашим DSL; перенести только недостающие операции и их проверки.
- [`src/repair.js`](https://github.com/NoblerWorks-HQ/minecraft-agentic/blob/master/src/repair.js):
  анализ блоков, которые игра не приняла, и исправление результата.
- [`src/critic.js`](https://github.com/NoblerWorks-HQ/minecraft-agentic/blob/master/src/critic.js):
  визуальная оценка и предложение исправлений.
- [`src/plans/reference-ops.json`](https://github.com/NoblerWorks-HQ/minecraft-agentic/blob/master/src/plans/reference-ops.json):
  примеры операций для модели.

проверялась исполнением. Мы не копировали их код в этом документационном изменении.

## Приоритет при переходе к окружению

| Ближайшая задача | Что проверяем первым | Что может остаться нашим кодом |
|---|---|---|
| Объёмный сектор, зал, шахта, переходы | mcbuild DSL + ProjectPlan/WorkPackages | Правила композиции сектора, связи уровней, ограничения пространства |
| Быстро увидеть варианты | Встроенные render/views/cutaways и agent loop | Оценка нужной эстетики, сравнение вариантов по критериям проекта |
| Сложные архитектурные операции | Наш DSL, затем `minecraft-agentic/src/ops.js` | Только отсутствующие примитивы с параметрами и проверками |
| Исправить провалы геометрии | Существующий edit loop, затем repair/critic Agentic Builder | Адаптер обратной связи к нашему миру и плану |
| Большой объём размещения | Текущие deltas/bridge; затем FAWE как кандидат с проверкой платформы | Недостающая очередь и бюджет действий для NeoForge |
| Память удачных решений | Текущий skill_store + механизм Voyager | Контракты наших навыков, поиск и композиция |
| Населить восстановленный сектор | MineColonies/Structurize как реальные моды и источники подходов | Связь состояния инфраструктуры с нашей прогрессией |

Наличие этих проектов не означает наличие готового универсального 3D-проектировщика,
симулятора произвольных модов или нужной архитектурной эстетики. Каждый закрывает
конкретный слой; сначала нужно использовать этот слой, а затем дописывать пробелы.

## Что пока не считать выбранным решением

Названия Structure Layout Optimizer, Structure Essentials, SparseStructures,
TerraBlender и TRender встречались в предыдущем контексте установленной сборки.
Это не доказывает их пригодность как API генератора или осознанный выбор для YAN.
Сохраняем как зацепки для поиска при подходящей задаче, без заявлений об интеграции.

APT упомянут в README Minecraft Agentic Builder как источник визуального review-подхода.
В этом проходе он отдельно не оценён; не подменять подтверждённые инструменты новой
цепочкой непроверенных рекомендаций.

## Следующее решение должно быть конкретным

Перед кодом нового генератора окружения зафиксировать:

- какие существующие entry points mcbuild используются;
- какие ограничения текущего ProjectPlan/DSL мешают выбранному сектору;
- какой внешний модуль закрывает каждое ограничение;
- что действительно приходится реализовать самим;
- как показать результат рендером и измерить время до первого превью.

Собственный код допустим там, где он связывает готовые части или реализует отсутствующую
проектную логику. Причина «забыли про обсуждённый инструмент» больше не должна определять
архитектуру.
