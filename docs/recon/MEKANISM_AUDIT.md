Исследован установленный `Mekanism-1.21.1-10.7.19.85.jar`:

Метод — чтение ресурсов JAR, индексация классов и сигнатуры/байткод через `javap`.
Общий проход: 2026 outer classes, 120 отобранных классов, 4519 semantic hits.

Архивы содержат manifests, пути data/recipe resources, список классов, bytecode,

В прежнем обсуждении UniversalMods обозначал направление интеграции

В них нет доказательства запуска universal-modder или готового универсального
экспортера всех правил модов. Не путать существующий аудит с планом его автоматизации.

`speed` — внутреннее значение прогресса транспортера. Его нельзя прямо объявлять
скоростью в блоках/тик без семантики движения из `TransporterStack/LogisticalTransporter`.

**Исправление прежнего пересказа:** утверждение «PULL минимум 11 ticks» не принимаем
как установленный универсальный закон. В восстановленном байткоде `LogisticalTransporter`
виден reset `delay=3`, а после неуспешного извлечения — backoff.
[Выдержка](mekanism/evidence/transporter_pull_delay.txt). Полный интервал зависит от
порядка обновлений и состояния; число 11 из старого чата не должно попасть в симулятор.

## Что есть и чего нет в этих результатах

Есть исходные механизмы и базовые численные параметры, достаточные для начала
MekanismTechnologyAdapter и событийной модели выбранных машин/сетей.
Есть bytecode для дальнейшего точечного чтения неизвестной семантики.

Нет полного resolved RecipeManager с datapack/tag overrides, effective world configs,
состояния upgrades и готовой математической модели всех конкурирующих сетей.
Это границы сохранённого экспорта. Получать недостающие данные следует прицельно;
они не требуют повторять общий аудит или заново проверять каждую плавку в игре.

Defaults из JAR и фактические параметры мира должны храниться раздельно.
Модель должна учитывать выбранный профиль/config/upgrades, а не подставлять defaults
как гарантированное состояние любой машины.

## Решение по дальнейшему развитию

Цель — проектирование под производственную задачу и реальный трёхмерный объём.
Готовые плоские factory layouts не являются конечным решением.

Данные аудита должны стать входом общей модели:

`capabilities + recipes + configuration + available volume + goal`

Далее: процессный граф → выбор машин/мощностей → 3D размещение и порты → отдельные
маршруты сетей → событийная симуляция → оценка вариантов → постройка.

Симуляция перескакивает между событиями, не ждёт физические игровые секунды.
Известные механизмы переиспользуются. Live-проверки нужны для неизвестного поведения,
расхождений с моделью и ввода новой конфигурации; полный тест каждой партии не должен
быть обязательным шагом генерации.

Проверка генератора: одна цель в низкой комнате, вертикальной шахте и объёме с
препятствиями должна давать разные компоновки без отдельных builders для каждого случая.

## Правило восстановления контекста

Перед предложением «давайте сделаем аудит Mekanism/UniversalMods заново» прочитать
этот документ, `oracle_defaults.json` и нужные исходные выдержки.
При нехватке данных назвать конкретное неизвестное свойство и проверить только его.
Не заявлять, что «всё уже автоматически извлечено», и не заявлять, что «аудита нет».
